# mandatecheck-mcp

MCP server that lets any AI agent use MandateCheck's payment safety gate as a tool.

The gate itself is the [`mandate-guard`](../packages/mandate-guard) package. This server holds no decision logic — it converts JSON into the gate's dataclasses, calls `evaluate()`, and returns what it says. No database, no web app, no state between calls.

## Installation

```
pip install -e packages/mandate-guard    # the gate (not yet on PyPI)
pip install -e mcp-server                # this server
pip install -e "mcp-server[llm]"         # optional: adds parse_intent's model client
```

## Running

Runs over **stdio** by default, the transport for local tool integrations:

```
mandatecheck-mcp
```

For a remote/multi-client deployment, use streamable HTTP:

```
MCP_TRANSPORT=streamable-http mandatecheck-mcp
```

Register it with an MCP client like this:

```json
{
  "mcpServers": {
    "mandatecheck": {
      "command": "mandatecheck-mcp",
      "env": { "GROQ_API_KEY": "..." }
    }
  }
}
```

`GROQ_API_KEY` is only needed for `parse_intent`. The other two tools never call a model and work without it.

## Tools

### `evaluate_transaction`

Checks one proposed payment against a mandate. Deterministic — same input, same decision, no model consulted.

```json
{
  "mandate": {
    "status": "active",
    "expires_at": "2030-01-01T00:00:00Z",
    "max_amount_per_txn": 500.0,
    "max_amount_per_window": 2000.0,
    "window_duration": 86400.0,
    "max_amount_total": 10000.0,
    "merchant_allowlist": ["bigbasket"],
    "category_allowlist": ["groceries"],
    "allowed_time_window": ["00:00", "23:59"],
    "original_intent_text": "Order groceries, up to 500 per order"
  },
  "transaction": {
    "transaction_id": "txn_01",
    "mandate_id": "m_01",
    "proposed_amount": 420.0,
    "merchant_id": "bigbasket",
    "category": "groceries",
    "source_content": "Weekly grocery list: milk, rice, vegetables",
    "agent_reasoning": "Restocking the weekly staples"
  },
  "context": { "seen_transaction_ids": [], "window_total": 0.0, "lifetime_total": 0.0 }
}
```

```json
{ "outcome": "ALLOW", "reason": "all checks passed", "flagged": false,
  "flag_reason": null, "evaluated_at": "2026-08-28T17:59:22.272264+00:00" }
```

The server is stateless, so the caller supplies `context` — what has already been spent and which transaction ids have already been used. A transaction carries no timestamp: the server stamps it with its own UTC clock, because a caller that can name the time can walk around the expiry and time-window checks.

### `check_mandate_status`

Whether a mandate is usable now and how much is left under its caps. Pure computation — no database, no model.

```json
{ "mandate": { "...": "same shape as above" },
  "context": { "window_total": 500.0, "lifetime_total": 1500.0 } }
```

```json
{ "status": "active", "reason": "mandate is active and not expired",
  "expires_at": "2030-01-01T00:00:00+00:00", "checked_at": "2026-08-28T17:59:22+00:00",
  "remaining_in_window": 1500.0, "remaining_total": 8500.0, "max_amount_per_txn": 500.0 }
```

### `parse_intent`

Turns a sentence into a **proposed** mandate for a human to confirm. The only tool here that calls a model, and its output never reaches an allow/block decision.

```json
{ "intent_text": "buy groceries, max 500 per order, only amazon" }
```

```json
{ "ok": true, "is_proposal": true,
  "note": "PROPOSAL ONLY — generated by a language model and not an active mandate. ...",
  "proposal": { "merchant_allowlist": ["amazon"], "category_allowlist": ["groceries"],
    "max_amount_per_txn": 500.0, "max_amount_per_window": 500.0, "window_duration": "7d",
    "window_duration_seconds": 604800.0, "max_amount_total": 2000.0,
    "user_facing_summary": "Allows buying groceries from Amazon up to 500 per order." } }
```

Without `GROQ_API_KEY`, or without the `llm` extra, it returns `ok: false` with an error saying what to install or set. It never crashes, and it never affects the other two tools.

## The rule that doesn't bend

The allow/block decision is never made by a model — a fixed set of checks, run in order, every time. `evaluate_transaction` and `check_mandate_status` make no model call and no network call at all. An agent can be manipulated; a hardcoded rule can't be talked out of what it's designed to check.

The `evaluate_transaction` tool uses the same detection logic that scored 96.67% recall on a blind held-out adversarial evaluation — see [eval/REPORT.md](../eval/REPORT.md) in the main repo.
